# Data Model (Phase 1 onward — field level)

> Turns the design principles in section 5 of [PLAN.md](PLAN.md) into concrete fields. The original Phase 1 scope was tenants/permissions, master data (business_partner/item/location) and the document framework skeleton. Fields specific to inbound/inventory/outbound documents were added in the matching phases.
>
> Naming conventions:
> - Table names are singular `snake_case`.
> - The primary key is always `id`; foreign keys are `xxx_id`.
> - Every business table has the "common audit fields" (section 0), which are not repeated per table.

## 6. Stock (implemented in Phase 2)

Stock changes only through `stock_service.apply_movements`, which writes a ledger entry and updates the balance in the same transaction.
- Balances cannot go negative, and a balance row is deleted when it reaches 0.
- All quantities are in the item's base unit.

### `stock_ledger`
| Field | Type | Description |
|---|---|---|
| `tenant_id` | FK→tenant | |
| `item_id` | FK→item | |
| `location_id` | FK→location | |
| `batch_no` | nvarchar(50) | Nullable |
| `expiry_date` | date | Nullable |
| `qty_change` | decimal(18,4) | Positive in, negative out |
| `movement_type` | nvarchar(30) | `RECEIVE`, `PUTAWAY_OUT`/`PUTAWAY_IN`, `MOVE_OUT`/`MOVE_IN`, `ADJUST_IN`/`ADJUST_OUT`, `COUNT_GAIN`/`COUNT_LOSS`, `PICK_OUT`/`PICK_IN`, `UNPICK_OUT`/`UNPICK_IN`, `SHIP_OUT`, `RETURN_IN`/`RETURN_OUT`, `REPACK_OUT`/`REPACK_IN` |
| `ref_document_line_id` | FK→document_line (nullable) | The document line that triggered the entry |
| `occurred_at` | datetime2 | Business time (may be later than created_at) |

### `stock_balance`

Updated in the same transaction as the ledger.
- The unique key is `(tenant_id, item_id, location_id, batch_no, expiry_date)`.
- SQL Server treats NULLs as equal here, so non-batch stock has one row per item + location.

| Field | Type |
|---|---|
| `tenant_id` | FK→tenant |
| `item_id` | FK→item |
| `location_id` | FK→location |
| `batch_no` | nvarchar(50) |
| `qty_on_hand` | decimal(18,4) |
| `qty_allocated` | decimal(18,4): quantity allocated to outbound orders but not yet picked; always `qty_on_hand >= qty_allocated >= 0`, and available = the difference |

Allocation is not a stock movement:
- Allocating increases `qty_allocated` directly, without a ledger entry.
- Posting or cancelling a pick releases it through `Movement.allocated_change`.
- Moves, adjustments and count losses can never take on-hand below the allocated quantity.

## 8. Document state machines

| Document | Status flow | Notes |
|---|---|---|
| PO purchase order | `DRAFT` →confirm→ `CONFIRMED` →receive→ `PARTIALLY_RECEIVED` → `RECEIVED` | Only drafts can be edited; draft/confirmed can be cancelled (→`CANCELLED`); partially received can be closed (→`CLOSED`) |
| GRN goods receipt | `DRAFT` →post→ `POSTED`; `DRAFT` →cancel→ `CANCELLED` | Posting writes stock, adds to the PO's received quantity and updates PO status. Over-receipt is rejected by default and allowed once the tenant enables `ALLOW_OVER_RECEIPT` |
| PUTAWAY | `DRAFT` →post→ `POSTED`; `DRAFT` →cancel→ `CANCELLED` | Target must be a BIN; may link a source goods receipt (which must be posted) |
| MOVE | Same as putaway | Between any two stockable locations (BIN/DOCK); no source document |
| ADJUST stock adjustment | `DRAFT` →post→ `POSTED`; `DRAFT` →cancel→ `CANCELLED` | Reason required; signed line quantities. `adjustment.create` can only create; posting needs `adjustment.post` (i.e. approval). Changing expiry/batch = two lines on one document: deduct the old dimension, add the new one |
| COUNT cycle count | `COUNTING` on creation →post→ `POSTED`; `COUNTING` →cancel→ `CANCELLED` | See below |
| SO sales order | `DRAFT` →confirm→ `CONFIRMED` →allocate→ `IN_PROGRESS` →ship→ `PARTIALLY_SHIPPED` / `SHIPPED`; `CLOSED`, `CANCELLED` | See "Outbound rules" below |
| PICK pick list | `OPEN` when created by allocation →post→ `POSTED`; `OPEN` →cancel→ `CANCELLED` (releases allocation) | Lines: from_location = bin, to_location = staging, qty_planned = allocated, qty_actual = picked |
| SHIP shipment (DO) | `DRAFT` →post→ `POSTED`; `DRAFT` →cancel→ `CANCELLED` | Only one DRAFT per order at a time; on creation it includes every picked but unshipped item for the order in staging |
| RETURN_IN customer return | `DRAFT` →post→ `POSTED`; `DRAFT` →cancel→ `CANCELLED` | Feature flag `RETURNS`. See "Extension module rules" below |
| RETURN_OUT return to supplier | Same | Feature flag `RETURNS`; line from_location = issuing location |
| REPACK | Same | Feature flag `REPACK`; consumed lines have only from_location, produced lines only to_location |

**Outbound rules**
- **Order lines**: `qty_planned` is the ordered quantity (in the order unit) and `qty_actual` the cumulative shipped quantity (base unit). Progress (allocated/picked/shipped/unallocated) is computed in base units from pick lists and shipments, not stored.
- **Allocation**: allocates "unallocated = ordered − allocated on open pick lists − picked" and creates one pick list.
  - Only BINs are used, excluding locked/inactive/counting locations and expired batches.
  - Order: first expiry first out (no expiry last) → pickable bins (`is_pickable`) first → first in first out (balance row creation time) → location code.
  - Candidate balance rows take `UPDLOCK`, so concurrent allocations never double-allocate.
  - If stock is short, whatever is available is allocated and the rest is returned as a shortage list.
- **Picking**:
  - Each line's picked quantity is confirmed (0 ≤ picked ≤ allocated, "set" semantics).
  - Posting deducts the picked quantity from the bin, releases the whole line's allocation and adds the picked quantity to staging.
  - A short pick returns the difference to "unallocated", which can be allocated again after replenishment.
- **Counting**: a count cannot start on bins allocated to open pick lists (otherwise count losses could not post, and picks could not post because of the freeze).
- **Close and cancel**:
  - Close requires no pick lists in progress, no unposted shipments and no picked but unshipped goods in staging.
  - Cancel requires no picks or shipments at all.

**Cycle count rules**
- **Creation**:
  - Locks the selected location rows and checks they are not in another count in progress.
  - Creates lines to count from current stock (book quantity snapshot).
  - Locked locations can be counted.
- **Freeze**: during `COUNTING` the covered locations are frozen. Receiving, putaway, moves and adjustments are all rejected (checked centrally by `get_stock_location`).
- **Entry**: entries have "set" semantics.
  - Entering the same location + item + batch + expiry again overwrites this round's quantity.
  - Combinations not on the book add a new line (book quantity 0).
- **Recount**: counted lines go back to "to count", and the next entry is the next round. Each round's counter and quantity are kept.
- **Posting requires**:
  - Every line is counted.
  - Every book balance on the covered locations has a matching line; otherwise the missing ones must be entered (enter 0 if there is nothing).
- **Differences**: difference = counted − book quantity **at posting time** (not the snapshot), written as `COUNT_GAIN`/`COUNT_LOSS` entries. Locations unfreeze after posting or cancelling.
- **Blind counts**: for users without `cycle_count.view_expected`, the API returns null book quantities.

**Extension module rules**

Feature flags are stored in `tenant_feature_flag` and switched under "System → Feature flags". When a flag is off, its menus are hidden and its API returns 403.
- **Customer returns**:
  - **Source order**: a return can link the original sales order. The customer must match, and the order must be partially shipped, shipped or closed. Lines map to order lines by item or `ref_line_id`.
  - **Quantity limit**: each line's cumulative returns (base unit, including posted returns) cannot exceed the line's shipped quantity. This is checked on creation and again on posting (with the order locked).
  - **Disposition**: `RESTOCK` puts goods into a BIN/DOCK (`RETURN_IN` entry); `SCRAP` is only recorded, not stocked.
  - The "returned" figure in order progress sums posted returns.
- **Returns to supplier**:
  - Supplier and return reason are required.
  - A return can link a received purchase order from the same supplier.
  - Posting writes `RETURN_OUT` entries and cannot use allocated stock.
- **Repack**:
  - At least one consumed line and one produced line.
  - Posting writes `REPACK_OUT`/`REPACK_IN` in one transaction; if any line is short, the whole document rolls back.
- **Cross-docking** (`CROSS_DOCK`):
  - Allocation can name a source DOCK, which cannot be the shipping staging location.
  - Stock is allocated directly from the receiving dock into a pick list; other allocation rules are unchanged.
- **Returnable assets** (`RETURNABLE_ASSET`):
  - `returnable_asset_type` (pallets, totes, etc.) + `returnable_asset_txn` entries (`ISSUE` lend is positive, `RETURN` is negative).
  - Outstanding quantities are summed per partner × type.
  - Recording locks the partner row, and returns cannot exceed what is outstanding.

**Location types**: `WAREHOUSE` / `ZONE` / `AISLE` / `RACK` / `BIN` / `DOCK`.
- Only `BIN` (storage bin) and `DOCK` (receiving/shipping staging) hold stock.
- Locked, inactive or counting locations cannot receive or issue stock.

**Concurrency control**:
- Every document change first takes `UPDLOCK` on the header.
- GRN posting always locks in the order GRN → PO.
- Stock balance rows are locked with `UPDLOCK, HOLDLOCK` in a fixed order (`stock_key`), preventing over-receipt, over-issue and deadlocks.
- Starting a count locks the location rows, so a location cannot enter two counts at once.

## 9. Integration framework (Phase 7)

Outbox pattern:
- When a document reaches a registered status (`app/core/event_catalog.py`, e.g. GRN→POSTED), a `before_flush` hook writes an `integration_event` **in the same transaction**. If the business transaction rolls back, the event rolls back with it.
- The delivery worker (`python -m app.worker`) dispatches events and calls the external systems.
- For the protocol see [integration.md](integration.md).

### `integration_connector` (external system connection)
| Field | Type | Description |
|---|---|---|
| `code` / `name` | nvarchar | `(tenant_id, code)` unique |
| `connector_type` | nvarchar(30) | Only `WEBHOOK` for now; dedicated ERP connectors will be added as types later |
| `endpoint_url` | nvarchar(500) | Push address; http/https only |
| `secret` | nvarchar(100) | HMAC-SHA256 signing secret; the API returns the full value only on creation/regeneration |
| `event_types` | nvarchar(max) | Subscribed event codes, JSON array |
| `extra_headers` | nvarchar(max) | Extra request headers, JSON object |
| `timeout_seconds` / `max_attempts` | int | Default 10 seconds / 8 attempts |
| `is_active` | bit | When inactive no new jobs are created; deletion is soft and unsent jobs are discarded |

### `integration_event` (events, the outbox)
| Field | Description |
|---|---|
| `event_type` | Event code |
| `status` | `NEW` (to dispatch) → `DISPATCHED` / `NO_SUBSCRIBER` |
| `document_id` / `doc_type` / `doc_no` | The source document |
| `payload` | Snapshot of the push content, taken at dispatch and unchanged across retries |
| `occurred_at` | When the event happened |

Index: `(status, created_at)`.

### `integration_job` (one delivery job per event × subscribed connector)
| Field | Description |
|---|---|
| `status` | `PENDING` → `RUNNING` → `SUCCEEDED` / `FAILED`; a failure with attempts left goes back to `PENDING` |
| `attempts` | Attempts in the current round; a manual retry resets it (a full set of attempts again) |
| `next_attempt_at` | Backoff: 30 s, 2 min, 10 min, 30 min, 1, 2, 4 hours |
| `locked_until` | Lease: set to +120 s when a worker takes the job; if the worker crashes it expires and another worker can take over |
| `last_status_code` / `last_error` / `completed_at` | |

### `integration_log` (one row per call)
| Field | Description |
|---|---|
| `attempt_no` | Increments over the job's lifetime |
| `requested_at` | When the call was made |
| `duration_ms` | Call duration |
| `status_code` / `success` / `error` | Outcome of the call |
| `response_body` | First 2,000 characters of the response |

### `worker_heartbeat` (system-wide)
The worker updates `last_seen` every round, and the UI uses it to show whether the worker is running.

**Concurrency and cleanup**:
- Dispatching and taking jobs both use `UPDLOCK, READPAST, ROWLOCK`, so several workers can run without double delivery.
- HTTP calls happen outside database transactions.
- Successful jobs and logs are kept for `INTEGRATION_RETENTION_DAYS` (default 90) days, then cleaned up; failed ones are kept until handled manually.

## 10. Report definitions

There are no summary tables; everything is computed from `stock_ledger` / `stock_balance` / documents (`stock_ledger` has an index on `(tenant_id, occurred_at)`).
- Days are split in `BUSINESS_TIMEZONE` (default Asia/Shanghai).
- Quantities are in base units.
- A query covers at most 366 days.

| Report | Definition |
|---|---|
| Inbound/outbound trend (dashboard) | Received = `RECEIVE` entries; shipped = `SHIP_OUT` entries |
| Stock turnover | **Received** = `RECEIVE` + `RETURN_IN`; **shipped** = `SHIP_OUT` + `RETURN_OUT`; **other** = adjustments, count gains/losses, repacks. In-warehouse transfers (putaway, moves, picks) are excluded. **Opening** = sum of entries before the start date. **Turnover** = shipped ÷ ((opening + closing) / 2); **days on hand** = days ÷ turnover |
| Picker performance | By the pick lines' `confirmed_by` / `confirmed_at`, excluding cancelled pick lists; fill rate = share of lines where picked = to pick |
| Expiring stock | On-hand balances with expiry ≤ today + N days (including expired) |
| Partner ledger | Entry → document line → the document's `partner_id`: receipts, returns to supplier, shipments, customer returns, summed per partner × item |

## 11. Performance conventions (settled after the Phase 8 load tests)

- **Indexes**: SQL Server does not index foreign keys automatically, so every column queried by foreign key needs an explicit index. Existing ones:
  - `document_header (ref_document_id)`
  - `document_header (tenant_id, doc_type, created_at)` (lists)
  - `document_line (ref_line_id)`
  - `document_line (confirmed_at) WHERE confirmed_at IS NOT NULL` (picker performance)
  - `stock_balance (location_id)`
  - `stock_ledger (tenant_id, occurred_at)` (reports)
- **READ_COMMITTED_SNAPSHOT**: enabled at the database level (migration db797d063f7a). Plain queries read row versions without shared locks. Anything that must be serialized uses an explicit `UPDLOCK` (document headers, balance rows, numbering rules) rather than relying on read locks.
- **Document numbers**: `next_doc_no` takes a number in a separate short transaction (its own connection pool) and commits immediately, so no lock is held for the business transaction. When the business transaction rolls back, the number is skipped, so numbers can have gaps.
- **List sorting**: `ORDER BY created_at DESC, id DESC`. The direction must match the index so the index can be read backwards directly.
- **IN lists**: SQL Server allows at most 2,100 parameters per statement. Fetch by ID in batches (`report_service.load_by_ids`) or join in SQL instead.
- **Opening/closing**: reports derive them as "current balance − later entries", scanning only the period's entries. This relies on "ledger total = balance", which posting guarantees in the same transaction and the tests verify across the whole database.

## 12. Data import

`app/services/import_service.py` handles master data, opening stock and orders.
- **Master data** (items, locations, business partners): upserted by code, inserting new ones and updating existing ones.
  - Columns missing from the file do not overwrite existing values.
  - Existing items cannot change their base unit, and existing locations cannot change their parent (it would change the path).
- **Opening stock**: rows with the same item + location + unit + batch + expiry are merged, and one posted stock adjustment is created with reason `OPENING` (opening stock).
- **Purchase / sales orders**: one row per order line. Rows with the same *Order ref* become one order; without a ref, rows with the same partner + date + remark are grouped. Every row of one order must agree on partner, date and remark. Lines with the same item + unit are merged. Each order is created as a `DRAFT` through the normal order service; the ref itself is only a grouping key and is not stored. At most 2,000 orders per file.
- **Commit**: validation runs first; nothing is written unless there are no errors, and the whole batch is one transaction.
